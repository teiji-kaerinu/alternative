5. TCP と UDP

トランスポート層の役割は 2 つ。 ① 通信の信頼性を確保する ② ポート番号でアプリを識別する。

TCP と UDP の比較

使い分けの理屈。 1文字でも欠けたら困るもの(Web・メール)は TCP。 多少欠けても止まらない方が大事なもの(生配信・音声通話)は UDP。 「確実さを取るか、速さを取るか」で覚える。

3ウェイハンドシェイク(接続の確立)

TCP は通信を始める前に、3回のやり取りで「準備できてる?」を確認する。

クライアント サーバ │ │ │──── ① SYN ──────────────────▶│ 「繋いでいい?」 │ │ │◀─── ② SYN + ACK ─────────────│ 「いいよ。そっちもいい?」 │ │ │──── ③ ACK ──────────────────▶│ 「いいよ」 │ │ │ データ転送開始 │

切断は FIN → ACK → FIN → ACK の4回のやり取り(4ウェイハンドシェイク)。

TCP の信頼性を支える仕組み

  • シーケンス番号 … データの何バイト目かを示す。順序がバラバラに届いても並べ直せる
  • 確認応答(ACK) … 「ここまで受け取った」と返す。一定時間ACKが来なければ再送する
  • ウィンドウ制御(スライディングウィンドウ) … ACKを待たずにまとめて送れる量を決めておく。 1個ずつACKを待つより圧倒的に速い
  • フロー制御 … 受信側が「もう少しゆっくり」とウィンドウサイズで指示し、あふれを防ぐ
  • 輻輳制御 … ネットワークが混雑してきたら送信量を絞る

ポート番号

16ビット(0〜65535)。「どのアプリ宛てか」を示す番号。 IPアドレスが建物の住所なら、ポート番号は部屋番号。

TCP/UDP チェックサム

通信の途中でビットが化けていないかを検出するための数値。 送信側が計算してヘッダに入れ、受信側が同じ計算をして確かめる。

計算方法(1の補数和)

  • ① データを16ビットずつに区切る
  • ② 全部を足す
  • ③ 桁あふれ(キャリー)は捨てず下位に足し戻す
  • ④ 結果をビット反転したものがチェックサム
送信側: 0xF0F0 + 0x1234 = 0x10324 ← 17ビット目にあふれた 0x0324 + 0x1 = 0x0325 ← あふれた1を下位に足し戻す ビット反転 = 0xFCDA ← これがチェックサム 受信側: 0xF0F0 + 0x1234 + 0xFCDA = 0xFFFF → 全ビットが1になれば「壊れてない」

計算範囲に「擬似ヘッダ」が入る

計算対象は TCP/UDP ヘッダとデータだけではなく、 IPヘッダから借りてきた擬似ヘッダ(pseudo header)も含む。

擬似ヘッダの中身どこから来る
送信元IPアドレスIPヘッダ
宛先IPアドレスIPヘッダ
プロトコル番号(TCP=6 / UDP=17)IPヘッダ
セグメント長計算値

IPアドレスまで含めるのは、アドレスが化けて別の相手に届いたパケットを受け取ってしまう事故を防ぐため。 L4 が L3 の情報も一緒に検算している。

NAT/NAPT と繋がる。 NAT は IPアドレスを、NAPT は IPアドレス+ポート番号を書き換える。 どちらもチェックサムの計算対象なので、NATルータは転送前に TCP/UDP チェックサムを計算し直している(→ 第7章)。
  • TCPは必須。UDPはIPv4では任意(未使用なら0)だが、IPv6では必須
  • 誤りを検出するだけで訂正はしない → TCPは再送、UDPは破棄
  • 16ビットしかないので検出能力は弱い。だから下位層でイーサネットのFCS(CRC-32)が別途守っている
