# Flaskでシステムを作るときの進め方（本人の持論）

2026-11-20、本人がFE（栢木）の知識と、ALTERNATIVEを作った経験から言葉にしたもの。
下の「答え合わせ」はClaudeが付けた。持論は本人が書き直していく。

## 本人の持論

1. まず頭に、汎用的なビジョン（全体の地図）を持つ。
2. 図を描く。
   - クラス図（UML）。ALTERNATIVEなら Spot や Form のクラス。
   - 表（テーブル定義）。クラス図で足りるかもしれない。
   - オブジェクト図（要るのか？）
   - アクティビティ図。自分の設計に沿って描く。
   - コミュニケーション図、シーケンス図。
3. 図があって初めて、app.pyの間取りがぼんやり浮かぶ。
   import → アプリの準備 → モデルのクラス → 具体的な動き（ルート）。
4. それができて初めて、Flaskを戦略的に使える。
   戦術（細かい書き方）は、自分の知識に無くても、公式ドキュメントやAIで解決する。
   これが、プロのプログラマーが日常的にやっていること。

## 答え合わせ

**全体として、合っている。** 先に形（何を作るか、どうつながるか）を決めて、細かい書き方はその都度引く。プロの日常はこれだ。

補足は5つ。

1. **図は「答えたい問い」があるときに描く。** 学習（FE対策）として全部描くのは良い練習になる。実務では、問いに合う図だけを選んで描くことが多い。
2. **クラス図と表は、両方あると強い。** SQLAlchemyのモデルは、クラスであり、DBの表でもある。クラス図は「何と何が、何対何でつながるか」を見せるのが得意。表は「型・空OKか・初期値」みたいな列の細部が得意。
3. **ルート（関数）はクラスじゃないので、クラス図には出てこない。** ルートの動きは、シーケンス図で描く。
4. **コミュニケーション図は、シーケンス図と同じ情報の別の見せ方。** 実務ではシーケンス図の方がよく使われる。
5. **戦術を引くにも、最低限の基礎は要る。** 公式やAIが出した答えが、自分の設計に合っているかを判断する力（引き継ぎ書のできることリストの J3）。

### オブジェクト図について

本人の理解「クラス図＝User・Spot・Visit。オブジェクト図＝お前のUser ── 加茂湖のSpot ── 12/26のVisit」は**合っている**。

- クラス図は設計図。オブジェクト図は、ある瞬間の実物（具体的な値の入ったインスタンス）とそのつながり。
- 実務で清書することは少ない。ただ、クラス図を描いたあとに「具体例を1つ当てはめて、つながりがおかしくないか確かめる」道具として役に立つ。中身が見えないと理解しにくいタイプには、特に効く。

## 図とapp.pyの対応

| 答えたい問い | 図 | app.pyのどこになるか |
|---|---|---|
| 何を保存するか。何と何がつながるか | クラス図（＋表） | モデルの区画（`class Spot`、`class Visit`） |
| 具体例で当てはめると、つながりはおかしくないか | オブジェクト図 | flask shell で実物を作って確かめる |
| 人（使う人）の流れはどうなるか | アクティビティ図 | どんな画面とルートが要るか、の洗い出し |
| 画面はどうつながるか | 画面遷移図（UMLなら状態マシン図） | ルートと `redirect` の行き先 |
| 1回のクリックで、誰が誰に何を頼むか | シーケンス図 | ルートの関数の中身（DBを取る → 画面を返す） |
| 入力欄は何か | 表（または画面の下書き） | フォームの区画（`class SpotForm`） |
